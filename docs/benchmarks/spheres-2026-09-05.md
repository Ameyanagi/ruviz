# Sphere rendering release measurements — 2026-09-05

The 147-atom Ru and 209-atom RuO₂ scenes render comfortably in the software
worker on this machine. GPU readback is not automatically faster at those sizes.
The 10,000-sphere case benefits from the GPU, but neither backend consistently
meets a 16.7 ms frame budget. These are worker measurements, not a claim of 60 Hz
end-to-end GPUI interaction.

## Method

- Apple M4, 32 GiB unified memory; macOS 26.5.1 (25F80); Rust 1.94.1,
  LLVM 21.1.8. Root crate wgpu 29.0.1, Metal adapter “Apple M4”.
- Release build of this change against base `dcc0e0b` (v0.12.2), default
  features plus `3d,gpu`. No geometry subsampling or drag quality reduction.
- 800 × 600 physical pixels, 96 dpi; software interactive rendering uses one
  sample per pixel; GPU uses four. Plot decorations and text are included.
- Each case runs in its own process. First-frame timing includes session
  preparation, worker/device/pipeline initialization, rendering, readback, and
  composition. OS/driver caches are shared between processes; this is not a
  guaranteed cold-start measurement.
- Orbit: 60 measured frames following five warm-up frames, 0.8° azimuth and
  0.15° elevation per frame. Timings include camera update and
  `BackgroundRenderer3D::render`, the worker path used by GPUI.
- Geometry update: 60 complete scene replacements, moving one atom by ±0.01
  data units and keeping the current camera. Includes builder/session/BVH
  reconstruction and rendering, not merely buffer writes.
- GPUI's final image upload, window composition, event-loop scheduling, and
  input-to-display latency are excluded. There is no isolated shader GPU timer.
- RSS is the process maximum from macOS `/usr/bin/time -l`. Unified GPU memory
  is not separately attributed. Upload bytes count geometry/texture uploads
  reported for the first frame, excluding uniforms and staging allocation.
- This was a shared workstation with other applications running. Short runs
  have scheduling and driver-cache noise; do not interpret small differences as
  statistically established improvements.

Synthetic atoms fill a deterministic 16-unit-wide cube with radius 0.35. Flat
markers use an 8-point diameter, so their screen coverage differs from physical
spheres. Ru and RuO₂ use radii 0.65 and 0.4 for metal and oxygen respectively.
All benchmark atoms are opaque; extensive faded context needs separate profiling.

The real clusters are reconstructed from symmetry-expanded COD lattice data in
[`molecules/mod.rs`](../../examples/support/molecules/mod.rs): Ru hcp, COD
9017842 (Mochalov et al., 1998), and RuO₂, COD 1548818 (Boman et al., 1970,
DOI 10.3891/acta.chem.scand.24-0116). Centering on Ru and including every atom
center within 8 Å gives exactly 147 and 209 atoms. The example asserts both counts.

## Orbit time

Each cell is **p50 / p95 in milliseconds**. “Unlit” retains exact sphere geometry,
surface depth, and picking; it disables only lighting. “Flat” is ordinary scatter.

| Dataset | CPU flat | CPU unlit | CPU shaded | GPU flat | GPU unlit | GPU shaded |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 100 | 5.36 / 5.52 | 6.56 / 6.80 | 7.65 / 9.57 | 7.79 / 10.02 | 9.38 / 10.62 | 14.04 / 14.83 |
| 1,000 | 6.65 / 6.94 | 10.33 / 14.77 | 10.58 / 11.24 | 9.36 / 11.72 | 14.21 / 17.66 | 14.52 / 16.51 |
| 10,000 | 9.22 / 9.73 | 32.68 / 60.52 | 45.68 / 52.04 | 13.40 / 14.57 | 25.01 / 40.90 | 24.19 / 35.75 |
| Ru 147 | 7.12 / 7.26 | 8.01 / 8.29 | 8.95 / 9.51 | 7.96 / 10.01 | 18.65 / 22.26 | 21.32 / 29.91 |
| RuO₂ 209 | 6.47 / 7.25 | 7.14 / 7.49 | 8.00 / 9.06 | 8.23 / 9.17 | 13.45 / 17.11 | 13.09 / 17.78 |

The non-monotonic GPU results reflect both screen coverage and run noise.
Software is a sensible starting backend for these ordinary cluster sizes.
For large scenes, profile the actual window resolution and atom radii; analytic
sphere work scales with covered pixels and overlap as well as atom count.

GPU spheres use 48 bytes per instance, compared with 16 bytes per flat marker.
Camera orbit retains geometry. Appearance changes replace the material scene
while retaining sphere geometry and the picking acceleration structure.
Faded spheres currently need one draw each for back-to-front sorting; opaque
spheres use instanced draws. Order-independent transparency remains future work.

## Flat-marker regression comparison

The same backwards-compatible
[`flat_marker_benchmark.rs`](../../examples/performance/flat_marker_benchmark.rs)
was compiled in release mode against the original `dcc0e0b` checkout and this
change. Three paired rounds alternate the execution order. Each run measures
60 frames after five warm-up frames. This separate comparison uses the original
`AxisAspect3D::Equal` API on both versions.

| Backend | Atoms | Original median p50 ms | Current median p50 ms | Change |
| --- | ---: | ---: | ---: | ---: |
| CPU | 100 | 5.659 | 5.662 | +0.1% |
| CPU | 1,000 | 6.758 | 6.284 | −7.0% |
| CPU | 10,000 | 8.746 | 8.684 | −0.7% |
| GPU | 100 | 8.009 | 7.769 | −3.0% |
| GPU | 1,000 | 9.242 | 8.911 | −3.6% |
| GPU | 10,000 | 12.388 | 12.563 | +1.4% |

There is no consistent slowdown in this sample. One early CPU 100 run had a
56 ms p95 scheduling outlier; all runs, including that one, are retained in the
[comparison CSV](spheres-flat-comparison-2026-09-05.csv). The FNV-1a hash of the
final RGBA image matches the baseline in all six cases and all three rounds.
The ordinary scatter shader is unchanged, and the extra GPU pipelines and
camera uniform are created only when a scene actually contains spheres.

## Reproduce

```sh
cargo build --release --features 3d,gpu --example sphere_benchmark --example flat_marker_benchmark
cargo run --release --features 3d,gpu --example sphere_benchmark -- cpu shaded ru
cargo run --release --features 3d,gpu --example sphere_benchmark -- gpu shaded ruo2
cargo run --release --features 3d,gpu --example sphere_benchmark -- gpu shaded 10000
cargo run --release --features 3d,gpu --example flat_marker_benchmark -- gpu 10000
```

Arguments are backend `cpu|gpu`, mode `flat|unlit|shaded`, and dataset
`100|1000|10000|ru|ruo2`. Set `RUVIZ_SPHERE_BENCH_FRAMES` to increase the sample
count. For process memory, run the built executable under `/usr/bin/time -l`
on macOS. Use separate Cargo target directories for baseline and current
checkouts to avoid reusing artifacts from different source trees.


The benchmark explicitly uses a `Camera3D` with equal data units and tight
framing for every compared mode. The interactive molecular example uses stable
scale and hidden axes; its screen coverage differs from these timing fixtures.
